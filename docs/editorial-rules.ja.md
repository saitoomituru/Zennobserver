# 記事・Bookの編集メタルール

2026-10-03: 会話で合意した編集単位を記録する。週次実行、更新・生成・分類・公開の自動処理を制定するものではない。

## 記事とBookの分け方

**記事は一つの問いを解説する単位、Bookは複数の問いを学べる順序に編成する単位。**
長さや抽象度だけで振り分けない。Sphereの設計判断も単独で理解できる問いなら記事にする。

| 形式 | 編集単位 | 読者に渡すもの |
|---|---|---|
| 観測記事 | 一つの試験・実験・Issueから取り出せる問い | 条件、操作、結果、そこからわかったこと |
| 切り分け記事 | 原因候補を絞った一連の試験 | 候補、変えた条件、判定、次の判断、再利用できる手法 |
| 設計記事 | 検証を支えた一つの仕組み・境界 | 必要になった理由と具体的な接続・実行例 |
| Book | 複数事例を通じた学習経路 | 前提→操作→切り分け→設計→応用を学べる章構成 |

一件のIssueから複数記事を作ってもよい。複数Issueを一つの切り分け記事へまとめてもよい。
一件・一試験という機械的な件数割りはしない。問いが独立する箇所で切る。
Bookも記事を時系列で束ねるだけにはせず、対象読者と到達点を定め、必要な章間説明を補う。
単独で読める記事とBookの該当章は相互参照する。全文の重複転載を既定にしない。

## 素材と判断の所在

資料候補はREADME・説明書だけでなく、Issue本文と議論、試験ケース、失敗ログ、修正差分、再試験結果を含む。
今回の静的台帳はリポ単位であり、各リポの全Issueを取得済みと意味しない。
記事化の際には、対象Issueの状態・議論・対応revisionを確認する。

切り分けの指示は都度、人間が出している。SphereDOSとManifestは、文脈・依存・実行条件・契約を参照できるようにし、
判断を実行へ渡す際の反復説明とプロンプト量を減らす仕組みとして説明する。
個別に自動化されている工程はその範囲を示す。人間の探索判断まで無人で行ったことに置換しない。

プロンプト圧縮を解説する事例では、次を接続する。

1. 人間が実際に出した指示
2. 指示が参照するManifest・実行契約・前提
3. 実行された操作と結果
4. 結果を受けた人間の次の指示

省略できた説明を示すことと、トークン削減率を計測したことは分ける。
削減率を書く場合は、比較対象、対象入力、計数方法、実行条件を添える。

山奥の一人ラボ、上下水道・電力・資金の制約は、この構造が必要になった設計条件として扱う。
制約を技術能力の割引理由にせず、研究継続や設備支援によって次に何を試せるかへ接続する。
状況は当該時点の本人の記述や記録に合わせ、過去の状態を無条件に現在へ引き継がない。

## noteの語り口をZennへ接続する

一人称は「私」を軸にした中性的な語りを既定とする。性別を演出する語尾や別人格を付加しない。
現場から話し、問いを立て、構造をほどき、短いユーモアと自分の判断を添える。
固有語・寺子屋・神話的語彙は原意を保持し、操作・構造・観測との関係を説明する。
技術向けにする際は、著者の立場や目的を消すのでなく、読者が検証できる情報を増やす。

| 保つもの | Zennで厚くするもの |
|---|---|
| 現場の制約、問い、語りの温度 | 実機・版・入力・実行条件 |
| 固有概念と設計哲学 | 対応する構造図、操作例、実在するパス・コマンド |
| 試行錯誤とユーモア | 期待結果と観測結果、原因候補を落とした理由 |
| 設計者としての判断 | 修正前後、回帰試験、再試験の導線 |

「トラ技寄り」は、この再現・測定・切り分け密度を高める編集方向を指す。
特定雑誌の文面を模倣する指示ではない。
観測した成果はその強さで書き、未知・未試験は該当箇所に置く。
自然な和文と定着した技術語を使い、識別子・コマンド・固有実装は原表記を保つ。
