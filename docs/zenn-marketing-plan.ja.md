# Zennマーケティング計画案

調査日: 2026-10-03。状態: **提案・未採用**。公開日程、記事生成・分類・自動追従の運用ルールを制定する文書ではありません。

## 提案の中心

Zennで届ける単位を「リポの紹介」「Docsの1ページ」から、**一つの読者課題に対する、実験で得た一つの成果・判断**へ変えます。

Quantaril / Sphereの固有概念と研究の方向性は残し、入口では読者が知っている技術名と困りごとを使います。本文でそれをFQuery、Fold、λ、ShowContinuityなどの設計へ接続します。一般的なAI解説より、一次ログ・実機条件・失敗・復旧の過程を強みにする計画です。

## 調査から読み取れる方向

公式方針と直近の掲載事例を確認しました。読者アンケート、全記事の閲覧数、検索ボリューム、順位の統計調査はしていません。以下の「需要」は検証する仮説であり、実測市場規模ではありません。「ベクトル」は読者の関心軸を整理する意味で使い、数値embeddingの生成や類似度計算は行っていません。

| 確認した事実 | 計画への反映 |
|---|---|
| Zenn公式は実体験、試行錯誤、対象読者・環境、冒頭で得られる情報の明示を推奨している [1] | 記事冒頭に課題・成果・対象環境を置き、元ログに戻れるようにする |
| AI執筆は禁止されていないが、著者による検証と経験・洞察が重視されている [2] | 自動整理の素材は一次記録に置く。確認できた結果と解釈・未検証を分ける |
| 記事を対象とする意味検索が追加された [3] | 固有名だけでなく「DAWが推論環境を起動できない」など課題を本文にも自然に記す。検索順位への効果は未検証 |
| ローカルLLMの検証記事には、問い・環境・実行例・結果表・失敗がある [4] | 同じ読者に届く候補として、FQueryの試せる入口とOpenRVCの実機ログを優先する |
| カメラとローカルLLMの実装記事にも、動く成果とボトルネックの説明がある [5] | システム全体の概説より、構築できた部分と残った制約を示す |

これは掲載記事の構成を観察したもので、これらの構成が高い閲覧数を生む因果関係は確認していません。

## 読者需要のベクトルと素材の対応

| 関心軸 | 読者の問い | 対応素材 | 記事で渡すもの |
|---|---|---|---|
| 試す・再現する | 自分の環境でも触れるか | FQuery playground、OpenRVC | 最短手順、環境、期待する出力 |
| 詰まりを解く | 何が原因で動かないのか | OpenRVCのCPU・DAW・runtime境界 | 症状、切り分け、成功条件、残る限界 |
| 比較して選ぶ | この方式はどの条件で使えるか | OpenRVCのoffline / realtime、FQueryの検証 | 同じ条件での観測と選択基準 |
| 設計を理解する | なぜこの境界・責務にしたか | Sphere、Fold NIC、OND800 | 選択肢、制約、決めた理由 |
| 新しい知見を得る | 既存の常識から何が変わるか | FQueryのλ判定、実験失敗・復旧記録 | 一次結果、考察、まだ言えないこと |

FQueryは「試す→設計」、OpenRVCは「詰まり→比較→設計」が入口候補です。OND800などの配信・ハードウェア群は、NDI・復旧の読者に向けた別の入口を作ります。全リポを同一のAI読者へ押し込む構成にはしません。

## 記事の粒度

文字数は日本語本文の**試行用の目安**であり、Zenn公式の推奨値や分析で求めた最適値ではありません。コード・図・参考資料の長さは別に考えます。

| 形式 | 一記事の範囲 | 本文目安 | 終了条件 |
|---|---|---|---|
| トラブル解決 | 一症状と一つの切り分け | 1,200–2,500字 | 原因・回避策・適用条件がわかる |
| ハンズオン | 一つの入力から成果まで | 2,500–4,500字 | 読者が再現し結果を比較できる |
| 実験・比較 | 一つの問いと条件付き結論 | 3,000–6,000字 | 判断に使える結果・限界がある |
| 設計解説 | 一つの境界・責務・選択 | 4,000–8,000字 | 別の実装にも持ち帰れる理由がある |

構成案: 冒頭150–250字で成果と対象読者 → 検証環境・revision → 最小の手順/図 → 実測・失敗 → 判断と限界 → 元コード・実験ログ。

生ログは元リポに残し、記事では結論に必要な抜粋・結果表を使います。独立した問いが複数あるときに記事を分け、全体の関係はシリーズ内リンクで示します。断片メモはScrap、体系化が必要な内容は後からBookの候補にします [1]。

## 最初の4週間・6記事の試行案

週1〜2記事は検証できる量を探すための仮置きです。公開を開始する日は未決定であり、以下は予約投稿ではありません。見出しも仮案です。素材の記録を著者が確認してから執筆します。

| 時期 | 記事候補 | 読者に渡すもの・素材の境界 |
|---|---|---|
| 1週目 | 「APIキーなしでFQueryのplaygroundを触る：Foldと評価の最小例」 | READMEにあるReact playgroundと最小操作。GUIの全機能成功は約束しない |
| 1週目 | 「Intel MacのCPUでRVCを動かす：GarageBandのオフライン書き出しで確認したこと」 | OpenRVCの実機記録。offline成功とrealtime未達を明示 |
| 2週目 | 「DAWからPythonを直接起動しない：OpenRVCの推論runtimeを分離した設計」 | AU・WebUI・gatewayの境界、起動と復旧の責務 |
| 3週目 | 「ツール呼び出し成功とタスク達成を分ける：FQueryのλをどう評価するか」 | 定義・判定例・失敗。API成功だけでは成果と言えない設計上の知見 |
| 3週目 | 「NDIソースの再出現にどう追従するか：OND800のShowContinuity設計」 | receiver再生成とdebounce、同名ソースの適用範囲。実機成功はログの範囲だけ述べる |
| 4週目 | 「ドメイン失効から考えた、識別子と通信経路の分離：Fold NICの設計」 | ManifestのIssueとfold-nicの設計。完全な独立性の実証とは区別 |

記事候補は[素材台帳](../sources/catalog.json)に固定したREADME・文書・実験ログから選んでいます。今回、各プロジェクトのbuild・実機テストを新たに実行したわけではありません。OpenRVCのREADMEでは、Intel CPUの130msブロックに対する推論約1.18秒はrealtime未達です。「CPUでリアルタイム成功」という宣伝には置き換えません。

## 読者に届く導線

1. **発見:** タイトルに既知の技術名・環境・課題を入れる。ブランド名はその具体例として使う。タグは関連する技術・環境・課題から3〜5個を試す。
2. **理解:** 冒頭で得られる成果を示し、最小実例と一次ログにより根拠を確認できるようにする。FQueryの抽象概念には操作例を添える。
3. **再訪:** 同じ読者課題の関連記事を1〜2本つなぐ。入口になる公開記事をプロフィールに固定する案 [6]。
4. **参加:** 結末に元リポのquickstartと実験ログへのリンク。「環境と結果を添えた再現報告」を促す。失敗報告も価値ある情報として受け取る。
5. **継続支援（任意）:** Sponsorsなどを使う場合、研究・検証を継続する使途を末尾の短い案内に置く。技術本文そのものに再利用価値を持たせる [1]。

記事公開後の外部告知は、使用中のSNS等で「課題・観測した結果・記事リンク」を一度共有する案です。本文の短いデモや結果図を再利用し、読者からの質問を追記や次の検証へ戻します。この計画では外部への投稿は実行しません。

広告購入、無関係な流行タグ、大量の記事投入を初手には置かず、一次成果に反応する読者層を確認する小さな試行から始めます。

## 測定と見直し

各記事について公開7日後・14日後の同じ期間で記録する案です。権限とサービス画面/APIで実際に取れる指標のみ使います。

| 目的 | 見る指標 | 次の判断 |
|---|---|---|
| 読者との接点 | 取得できる閲覧指標、いいね、フォロー増分、具体的な質問 | 見出し・冒頭・対象読者が合っているか |
| 再現・利用 | 環境付きの再現報告数、利用上のIssue、GitHubの参照元・訪問・clone | 手順記事を増やすか、失敗の切り分けを足すか |
| 深い関心 | 設計への質問、関連実装・PR、次記事を求める反応 | 設計シリーズを伸ばすか |
| 継続支援（採用した場合） | 継続支援者数・月額・継続期間 | 読者との関係が研究継続につながるか |

GitHubの集計やフォロー増分から個別記事の厳密な転換率は計算できないことがあります。初月は自分たちの基準値を作り、少数の反応を一般化しません。閲覧があって再現報告がない場合、CTA・環境・手順を見直します。質問が集まった課題は次の候補にします。改善ごとに見出し、冒頭、題材など一つの要素を変えます。既存記事の履歴比較は対照群付きA/Bテストではありません。

## 次に決めること

入口2記事の選定、公開先アカウント、読者報告を受ける場所、計測可能な指標、公開確認を担当する人を決めれば試行できます。iPad等から確認する選択肢として、個人リポのPR下書きプレビューも提供されています [7]。

この文書の追加によって、運用フロー・週次automation・自動分類・Issue起票・公開設定を変更してはいません。
